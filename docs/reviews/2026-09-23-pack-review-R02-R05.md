## Cross-pack observations

1. **Negative verdicts from unconfirmed candidates (D212(b)).** R05 v1 set the pattern: a candidate that would rule the order out is asked, never failed on (`r05_late_order_v1.ts:476–497`), `unsupportedReason` is set only from known cells (`:544`), and `notYetDue` is set only from known facts. R02 and R04 do not follow it (R02-01, R02-11, R04-02). R05 itself misses it inside the 5c branch (R05-03) and on the unknown-zone path (R05-02). The rule comes from contract §4 rule 3 ("not_eligible (from known facts only)"), rule 4b and §2.5. **Recommendation:** record D212(b) as a cross-pack ruling. A negative, not-yet-due or review verdict never rests on an unconfirmed candidate: a candidate-driven fail becomes `unknown` with reason `candidate_unconfirmed`. The R04 verifier notes the defect is systemic, because the engine's generic leaf evaluation treats candidates as usable (`isUsable`). M20 may therefore offer one shared guard (engine item E3), or each pack can fix it locally.
2. **Firm counterparty dates from unconfirmed or assumed inputs (D154(2) extended).** Four findings: R02-04, R02-06, R02-07 and R05-05. D154(2) covers anchors. The same principle should cover a timer's **selector** (`appliesWhen`), the **assumptions** that move its date, and an **unknown zone**. A counterparty timer shows a firm `dueAt`, `overdue` or `escalate` only when all three are known. Until then it is `unknown_anchor`, or its overdue status waits for the latest plausible zone.
3. **Unknown-zone conventions differ.**
   - The R02 and R04 compliance gates resolve an unknown zone toward `eligible` with no assumption (R02-12, R04-07).
   - R05 asks for the zone, except on the New York fail path (R05-02).
   - The engine's timer fallback takes the earliest-ending zone whatever the obligor (R02-06).

   **Recommendation:** one convention per purpose. Gates use README rule 5 (unknown → capped with an assumption). Counterparty overdue waits for the latest zone. User windows keep the earliest zone, as today.
4. **Adapters run without a trigger.** R04 emits three runs on every air transaction (R04-15). The R02 and R05 adapters also emit one `txn` run per transaction, so this is a platform pattern. R04 is the pack whose spec states an explicit trigger.
5. **Double counting across paths and packs.**
   - R02's ancillary total against R04 path a (R02-15);
   - the bag fee entered as a path-b expense line (R04-13);
   - bag identity (R04-05, R04-06).

   The per-transaction air paid cap was not implemented at `3d5cb7f` (`recovery.ts:446`).
6. **Next actions drop `candidate_unconfirmed` keys on `needs_facts`.** Found in R04 (R04-18). R02 has the same filter (`r02_air_refund_v1.ts:827`); the verifier suggests a probe, and it is not a finding here. R05 keeps them (`r05:820–822`).
7. **Truthful explanations.** R05-01 (legal conclusions on excluded or unverified results), R04-19, R02-22 and R02-24.
