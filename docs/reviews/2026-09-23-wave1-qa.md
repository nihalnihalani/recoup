## 1. Core financial fixtures (`convex/ledgerFixtures.test.ts`, 27 tests)

Every user action goes through the public API. Three data boundaries are crossed below it; each is where an external party's data enters, never a shortcut past a user decision:
- **`intake.applyExtraction`:** the model output. The holder's one-tap `confirmRefundEmail` follows it (DA-B-3, D198).
- **`priceWatch.recordCheck`:** the scraper output.
- **`policies` and `priceChecks` rows.**

The expected numbers are written by hand. `recovery.summary` is checked at every step, per currency: every tile as `[amount, provisional, components]`, Recovered, over-credit, I1 (Σ tiles = Σ outstanding), I2 (Recovered + over-credit = Σ net) and I3 (each open component is in exactly one tile).

| Block | What it checks |
|---|---|
| A | The mission's walk: 4,000 → promise 4,000 → confirm 1,500 → confirm 2,500 → later debit 1,000, with balance, status and tile at each step. A "posted" refund email is still only a promise. |
| A2 | C4's example: 2,500 in Ready. A packet → Asked, user-reported. |
| B | N5: provisional 2,000 shown "of which provisional"; `ProvisionalOutstanding`; separate posting; finalize adds 2,000; reverse; a provisional credit in the wrong currency is refused. |
| C1, C2 | Alternatives never inflate Potential or Recovered. The excess shows on the over-credit line. |
| D | USD and EUR are separate rows. |
| E | A voucher is a count only. |
| F | A EUR refund email on a USD purchase → needs_review. |
| G | R01 2×12,000 → 9,500 opens one 5,000 claim in both modes. Wrong variant, product or currency, or no policy → no claim. |
| H, H2 | The paid-total cap. |
| I | JPY → `unsupportedCurrencies`. |
| C4 | Below. |

**C4 (contract rev 5 §3.4 I3; D195, D196): the independent generator.** This is QA's own sweep, not M12's generator in `recovery.test.ts`.
- **Main generator:** every claim status (9) × every delivery state (none, draft, approved, queued, unknown, failed, sent). It runs three fixed-seed passes (mulberry32). Each pass draws the remaining dimensions:
  - promised: none, 1,000 (below net) or 9,000 (above net)
  - provisional: 0 or 1,500
  - refusal: none, newest, answered by a newer question, or followed by the claim's money
  - a linked opportunity: none, `case_open`, or `open` carrying `activeClaimId`
  - an alternative open opportunity: none, 3,000 or 7,000
  - a credit: 0, 2,000, 5,000 or 6,000 (6,000 is above the ask)
  - a debit: 0 or 1,000
- **Eight two-claim cases:** a double credit, an open member beside a confirmed member, a dismissed credited member, refused vs promised and refused vs asked members, and a confirmed claim with an alternative.
- **The oracle** comes from §3.4 and D196:
  - nodes; open = not closed-for-ask
  - lossAll and lossOpen
  - recovered = min(Σ net, lossAll)
  - outstanding
  - the furthest-state tile: promised > refused > asked > sending > ready > potential
  - provisional = min(outstanding, Σ)
  - the D196 excess split: red only with ≥ 2 credited claims in the component, otherwise neutral
- **Result:** the summary equals the oracle on all 197 cases, with no mismatch.
- **Sensitivity:** a separate test asserts that every dimension value occurs and that every tile and both excess lines are exercised. Two deliberate oracle mutations make the sweep fail:
  - swapping the refused and asked ranks;
  - counting an answered refusal, or one followed by money, as refused.

## 2. R01 parity against `5cc326d` (`convex/r01Parity.test.ts`, 84 tests)

**Method.**
- The 39 scenarios sit between the `// <scenarios>` and `// </scenarios>` markers. They are self-contained: they seed rows as the pre-mission code stored them, then drive `priceWatch.recordCheck` through timed observations.
- The recorder copies that block verbatim into a throwaway test in a worktree at `5cc326d` and runs it against that revision's own code. The resulting projections were pasted unchanged as `EXPECTED_5CC326D`.
- The test file runs every scenario twice:
  - `legacy`: no active pack.
  - `v1`: R01 v1 forced active through the test-registry seam.
- The only allowed difference is D160, the JPY scenario. The test asserts that difference is really present.
- v1-only checks cover DA-A-2, DA-A-3, N7 (A-T2) and D160.

**Re-verification (after D209).** The original recorder was lost with `/private/tmp`, so it was rebuilt from this description and re-run at `5cc326d` on 2026-09-23. Its output is deep-equal to the committed table: 39 of 39 scenarios.

**The recorder** (`record-parity.mjs`; run it from a worktree at `5cc326d` with `node_modules` linked):

```js
// node record-parity.mjs <path to the current convex/r01Parity.test.ts> <out.json>
import { execFileSync } from "node:child_process";
import { readFileSync, rmSync, writeFileSync } from "node:fs";
import path from "node:path";

const [source, out] = process.argv.slice(2);
const text = readFileSync(source, "utf8");
const start = text.indexOf("// <scenarios>");
const end = text.indexOf("// </scenarios>");
if (start < 0 || end < start) throw new Error("scenario markers not found");
const block = text.slice(start, end + "// </scenarios>".length);
const head = execFileSync("git", ["rev-parse", "--short", "HEAD"], { encoding: "utf8" }).trim();
if (head !== "5cc326d") throw new Error(`run me in a 5cc326d worktree, not ${head}`);

const recorder = `/// <reference types="vite/client" />
import { afterEach, beforeEach, it, vi } from "vitest";
import { writeFileSync } from "node:fs";
import { internal } from "./_generated/api";
import { setup } from "./test.setup";

${block}

beforeEach(() => vi.useFakeTimers());
afterEach(() => vi.useRealTimers());

it("records the 5cc326d projection of every parity scenario", async () => {
  const out: Record<string, unknown> = {};
  for (const s of SCENARIOS) {
    const t = setup();
    const { projection } = await runScenario(t, s, internal.priceWatch.recordCheck, (ms) => vi.setSystemTime(ms));
    out[s.id] = projection;
  }
  writeFileSync(process.env.PARITY_OUT!, JSON.stringify(out, null, 2));
});
`;
const file = path.resolve("convex/zzParityRecord.test.ts");
writeFileSync(file, recorder);
try {
  execFileSync("npx", ["vitest", "run", "convex/zzParityRecord.test.ts"], { stdio: "inherit", env: { ...process.env, PARITY_OUT: path.resolve(out) } });
} finally {
  rmSync(file);
}
```

## 3. Two-user isolation (`convex/isolationM1.test.ts`, 29 tests)

**Probes.**
- User B calls every new id-taking public function with user A's id, and again with a deleted id. The outcome must be the same masked error or value both times.
- A's rows in 16 tables stay unchanged, and no error carries a secret.
- The 21 probes: `transactions.get` and `forPurchase`; `facts.list` and `answer`; `evidence.get`, `declareDocType` and `setPinned`; `opportunities.openCase`, `dismiss`, `get`, `forTransaction`, `forPurchase` and `reevaluate` (by purchase and by transaction); `drafts.prepareSend` and `resendAfterUnknown`; `intake.confirmRefundEmail`; and `claims.recordProvisionalCredit`, `finalizeProvisionalCredit`, `reverseProvisionalCredit` and `recordNonCashRemedy`.

**Lists and routes.**
- `transactions.list`, `recovery.summary` and `intake.needsAttention` show B nothing of A's.
- A refund email from B's address never touches A's claims.
- `GET /evidence/file` returns one identical 404.
- Upload dedupe never crosses users.

**Coverage guard.** The guard enumerates every public function reflectively (`import.meta.glob`, `isPublic`) against the `5cc326d` baseline. Any new function without a probe shows up as an `it.todo`. There were none at `77110bd`, after R02/R04/R05 landed.

## 6. Limitations

- **convex-test runs one mutation at a time.** The concurrency results rest on the read-set arguments in the file header together with both serial orders, not on true parallel execution.
- **The alternatives in fixtures C1/C2 and in the C4 two-claim cases are seeded.** Wave 1 has one remedy per loss, so no public path yet puts two remedies on one loss key. C4 inserts rows directly for every case, because most of its combinations have no single public path.
- **A merchant's promise enters at `intake.applyExtraction`.** The model call itself is not exercised.
- **The browser run seeds four provider stand-ins (D202).** Draft generation, policy research, the price scrape and inbox provisioning have placeholder keys on dev. Real-provider behaviour stays BLOCKED_EXTERNAL (D83).
- **No real send was exercised,** by design: the recipient box is never ticked, and `sendTrace` proves nothing was queued.
- **The C4 oracle applies D196's "red" rule only to components with ≥ 2 credited claims.** A single component that mixes a claim credited above its own ask with a second credited claim is not generated: D195/D196 do not say how such an excess splits.
