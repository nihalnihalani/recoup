## Settled questions

1. **Password `verify`/`reset` shape.** Both are `EmailConfig`s built with `Email({ id, maxAge, generateVerificationToken, sendVerificationRequest })`. The **library** generates the code (`signIn.ts:126` calls our `generateVerificationToken()`, else a 32-char string), stores `sha256(code)` in `authVerificationCodes` with `expirationTime = now + maxAge*1000` (one pending code per account; a new request deletes the old), then calls `sendVerificationRequest({ identifier, url, token, expires, provider, request, theme }, ctx)` — `token` is the plain code, `url` embeds it (never use it), `ctx` is the auth action ctx passed as a **second argument the type does not declare** (`signIn.ts:168`). `emailVerificationTime` is set by the library: `verifyCodeOnly` → `upsertUserAndAccount(type:"verification", {email, emailVerified:true})` → `users.emailVerificationTime = Date.now()` and `authAccounts.emailVerified = email` (`users.ts:127,213`). A reset code also verifies the email. Distinct ids (`recoup-verify`, `recoup-reset`) are required: codes are bound to the issuing provider (`verifyCodeAndSignIn.ts:154`).
2. **`sendMessage` from an internalMutation**: yes — it is `ctx.runMutation(component.lib.enqueueSend)` (`client/index.js:72`); `drafts.approveAndSend` already does it.
3. **`onEvent`**: enqueued via the component's `callbackPool` (separate transaction, `lib.ts:483`) with `{ event: AgentMailEvent }` for **every** event type including `message.received`. It carries **no outboundId**; only AgentMail's `message_id` inside `message|send|delivery|bounce|complaint|reject` (`eventLogic.ts:extractIndexFields`). Mapping must go through a stored `agentmailMessageId`.
4. **D68 boundary**: kept — see T06(d).
5. **Rate limiter**: 0.4.0, peer `convex ^1.43.0` → compatible with 1.46.0. It nests `@convex-dev/batch-worker@0.3.4` (`component.use(batchWorker)`), which needs `convex-helpers ^0.1.119` (installed 0.1.124). convex-test registration below.

## T05

**(g) Corrections to the planner's contract**
1. `Password()` returns `ConvexCredentials({...})` whose top-level `authorize` is a stub (`async () => null`); the real one is `options.authorize`, merged at materialization (`provider_utils.ts:96-101`). Wrap it as `ConvexCredentials<DataModel>({ ...password.options, authorize: guardedAuthorize })` (one documented cast to read `options`); this preserves `id:"password"`, `crypto`, `extraProviders`.
2. **Normalize `params.email` inside `guarded` and pass the rewritten params through.** `profile()` only normalizes the account id; the library then patches `users.email` with the *raw* `params.email` at every code creation (`createVerificationCode.ts:52-60` → `users.ts:134`) and `Email().authorize` rejects a code when raw `params.email !== providerAccountId`. Without this, "Foo@Example.com" signs up and can never verify.
3. Reset for a known address makes `Password.authorize` return **`null`** (`signInViaProvider` maps `started` → null), which the client sees as `{ signingIn:false }`. For unknown addresses `guarded` catches `Error("InvalidAccountId")` and returns `null` — not `{ kind:"started" }`. To keep rate-limit errors indistinguishable, `guarded` runs `rateLimiter.check(ctx,"authMailPerEmail",{key})` for `flow==="reset"` and throws the same ConvexError when `!ok`.
4. `sendVerificationRequest` is typed with one parameter; declare `ctx` as an optional second parameter (`ctx?: GenericActionCtxWithAuthConfig<DataModel>`, assert at runtime) or typecheck fails.
5. `@oslojs/crypto/random.generateRandomString(random, alphabet, length)` needs a `RandomReader` (`{ read: (b) => crypto.getRandomValues(b) }`).
6. "All other errors pass through" is wrong for production: plain `Error`s reach clients as "Server Error". `guarded` maps `InvalidAccountId|InvalidSecret` → `ConvexError("Wrong email or password")`, `TooManyFailedAttempts` → `ConvexError("Too many attempts…")`, `"Could not verify code"|"Invalid code"` → `ConvexError("That code is not valid or has expired")`, `"already exists"` → the planner's generic sign-up message. Same message for known/unknown addresses (timing side channel accepted).
7. Tests need `SITE_URL` (`redirects.ts:57` is hit on every code send), `CONVEX_SITE_URL` and a PKCS8 `JWT_PRIVATE_KEY` (generate once with `jose`'s `generateKeyPair("RS256")`/`exportPKCS8`) — the successful-code path mints a JWT.

**(b) Signatures:** `normalizeEmail(raw: unknown): string`; `authMail(kind: "verify"|"reset"): EmailConfig` with `id: recoup-${kind}`, `maxAge: VERIFICATION_CODE_TTL_S`; `authMailTransport = { send(args: { to: string; kind; code: string; expiresInMinutes: number }): Promise<void> }` (object indirection so `vi.spyOn(authMailTransport,"send")` works, as `agentmail` is spied today); `guardedPassword` provider; `convexAuth({ providers: [guardedPassword] })`.

## Scheduled mail to deleted / opted-out / unverified users

- Alerts: closed by the send-time gate in `sendDrop`, and both sweep-rescheduled and re-claimed rows pass through it.
- **Open:** a tombstoned (`deleting`) account whose `authAccounts` row is not yet purged can still request a verification/reset code and mint a *new* session. Close it with the `requireUserId` tombstone check above and by having T18 purge `authAccounts/authSessions/authRefreshTokens/authVerificationCodes` first.
- **Open:** a `queued` alert already handed to the component is delivered even if the user opts out or deletes in the retry window. T18 should `agentmail.cancel` the user's queued `mailLog` outbounds best-effort (D57 pattern); otherwise document.
- Auth mail deliberately ignores `alertSettings` (opt-out covers alerts only). Recommended: refuse auth mail to addresses with `suppressedReason:"complained"` (lookup via `users.email` index) — a should, not a must.
- Accepted: `authAttempt` keyed by email lets anyone slow a victim's sign-in to ~1/min by spamming reset requests; 8-digit codes are looked up globally by hash with `.unique()`, so a collision between two pending codes fails both (negligible at this scale).
